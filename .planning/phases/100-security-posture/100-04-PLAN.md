<objective>
Close criterion 2. Two views read `auth.users` and hand `email` and `raw_user_meta_data` to any
authenticated caller: `entity_comments_with_details` and `upcoming_milestones`.

They need different fixes, and this is the plan's whole point. `authenticated` holds NO grant on
`auth.users` (verified: `has_table_privilege('authenticated','auth.users','SELECT')` is false), so
setting `security_invoker` on a view that joins it turns a leak into a 500. `entity_comments_with_details`
must therefore stop reading `auth.users` FIRST - its three joins move to `public.users`, which carries
`id, email, username, full_name, avatar_url` - and only then be converted. `upcoming_milestones` has no
application caller at all, so it is restricted instead.

The acceptance is the **end state of each named view**, not the absence of a dependency: what each view
IS afterwards, printed row by row from the catalog.
</objective>
