<objective>
Put Elected Officials on the two NAV-01 surfaces that are missing it — the live sidebar and the
dossier hub type cards — WITHOUT shipping the fabricated zero that adding it naively would produce.

**Why the count is the hard part, in one derivation.** `elected_official` is not a `dossiers.type`
value at all (the migration shrank the CHECK to 7); it is `persons.person_subtype`. So the hub's
counts query can never produce an EO bucket, and there are THREE places that turn that absence into
a confident `0`:

1. `services/dossier-api.ts:702-711` — bucket init over the DB-7. **Correct as it stands; 97-04
   made it derive.** The fix here is that it is NOT widened, and the EO count comes from the EO
   source instead. Widening it would create a bucket no query can ever fill.
2. `DossierListPage.tsx:456-458` — the map build: `if (!typeCount) map[type] = { count: 0, … }`.
3. `DossierListPage.tsx:582-587` — the render fallback `typeStatsMap?.[type] ?? { count: 0, … }`.

The shipped em-dash treatment exists ONLY inside the `countsError` branch (`:565-574`) and is
inherited by none of the three. `RULING-P97-04 §1` is explicit that a render-site-only fix is
partial and would read as closed.

**And the em-dash is the FLOOR, not the ceiling.** A real total exists —
`ElectedOfficialListResponse.total` — so this plan ships the real number for the figure that HAS a
source and the em-dash for the figures that genuinely do not. That composition is the honest one:
the EO list response carries no active/inactive split, and inventing one would trade a single
confident lie for two.

Purpose: the eighth type becomes reachable without the phase shipping the defect it exists to kill.
Output: two surfaces, one root-cause count fix that applies to all eight types.
</objective>
