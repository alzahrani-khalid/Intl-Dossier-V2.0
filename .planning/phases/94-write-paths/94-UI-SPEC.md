# Phase 94 — UI Design Contract

> Visual and interaction contract for Phase 94: Write Paths. Generated by gsd-ui-researcher,
> verified by gsd-ui-checker. Sources: `94-CONTEXT.md` (D-04/D-05/D-08..D-13/D-33 are the
> UI-binding decisions), `94-RESEARCH.md` (seams pinned by `file:line`), `frontend/DESIGN.md`
> (Linear spec, dark-canonical), `frontend/src/design-system/CLAUDE.md` (runtime token engine),
> and the shipped components under `frontend/src/components/`.

**Scope discipline:** this is a defect-repair phase, not a design phase. Its UI surface is small
and almost entirely error/affordance states: two kanban reject messages, one non-droppable
affordance, one degraded row state, one translated error string, and one button-enablement
contract. No new pages, no new navigation, no new layouts, no new button variants, no new visual
language. Linear dark is the only direction; the IntelDossier prototype is historical reference
(superseded 2026-07) and nothing here points at it. Reuse Phase 93's shared error vocabulary
(`QueryErrorState`, the `role="alert"` + translated-copy pattern) — never author new error markup
(D-11).

## Interaction Contracts

### 1. Kanban reject messages — two distinct causes, two distinct keys (D-08, RULING-P94-03 order 3)

**A single generic "cannot move" string is REFUSED.** The existing
`unified-kanban:errors.invalidTransition` ("Cannot move to {{column}}") does NOT satisfy criterion
4 — it names neither the real reason nor a remedy. Two new key pairs land in the EXISTING
`unified-kanban` namespace (registered in both locales; `errors` object already present in
`en` and `ar`):

- **Cause (i) — the board's `review` stage has no counterpart in the commitment lifecycle.**
  Fires when a drop still resolves `review` for a commitment (e.g. a drop onto a card inside the
  Review column). Refused at the mutation layer BEFORE the write.
- **Cause (ii) — the drag would be coerced because the commitment is past its due date.**
  Fires when the write would satisfy the DB trigger's own condition (`due_date < CURRENT_DATE` and
  the status about to be written is `pending` or `in_progress` — mirror the condition, never
  paraphrase it, D-33). The message MUST name the derived state AND the remedy the trigger itself
  honours: extend the due date, or complete the commitment. Refused BEFORE the write — never a
  success signal followed by a snap-back.

**Render surface:** the board's existing toast channel (`useToast` → react-hot-toast), destructive
variant. **`role="alert"` is an acceptance criterion** (RULING-P94-01 order 1): react-hot-toast
defaults to `role="status"` / `aria-live="polite"`, so the reject toast must pass
`ariaProps: { role: 'alert', 'aria-live': 'assertive' }` (supported per-toast by the installed
react-hot-toast). The `useToast` wrapper (`hooks/useToast.ts`) does not forward `ariaProps` today —
extending its options or calling `toast.error` directly with `ariaProps` is planner discretion; the
contract is the rendered `role="alert"` + both translated strings, verified in the DOM, not the
mechanism. Toast chrome itself is existing app chrome — no restyle, no new toast variant.

**The repaired generic failure toast (D-08's in-scope violation):** `useUnifiedKanban.ts:481-485`
currently renders a hardcoded English title + raw `error.message`. It becomes the EXISTING keys
`unified-kanban:errors.updateFailed` + `errors.updateFailedDescription` (both locales already
present — zero new keys for this repair). Raw `error.message` goes to `console.error` only, never
to the DOM.

### 2. Non-droppable affordance — the `review` column during a commitment drag (D-04, D-33)

- While a commitment card is dragged, the Review column's droppable is disabled
  (`useDroppable({ disabled })` in `BoardColumn.tsx:138`, reading the active drag via
  `useDndContext` — which must be added to the `@/components/kanban` barrel; direct `@dnd-kit/core`
  imports are ESLint-banned outside `components/kanban/*`). **The affordance contract: the Review
  column paints NO drop affordance — no `isOver` ring, no drop indicator, no cursor invitation.**
  No additional de-emphasis treatment (no opacity change, no new chrome) — absence of the drop
  signal IS the affordance. dnd-kit excludes disabled droppables from collision candidates, so
  this falls out of `disabled` without new CSS.
- **Trap 1 — `closestCenter` retargets, it does not nullify.** A release over the disabled Review
  column lands on the nearest ENABLED column. This is tolerated ONLY because (a) the user was shown
  no "will drop here" signal on Review during the drag, and (b) the landing is fully visible — the
  card renders in the landed column with the standard drop feedback, and Escape cancels mid-drag.
  The mutation-layer reject (contract 1) remains the load-bearing guarantee regardless.
- **Trap 2 — cards inside Review are droppables of their own** (`useSortable`, not disabled). A
  drop onto a review-resident card resolves `review` as the target stage and reaches the mutation
  layer — which refuses it with cause (i). Disabling the card-level droppables during a commitment
  drag (`useSortable({ disabled: { droppable } })`, expressible in `@dnd-kit/sortable@10.0.0`) is
  permitted UX polish, not required; the reject is the requirement.
- **Past-due predicate (D-33):** during a drag of a past-due commitment, columns whose mapped
  status is `pending` or `in_progress` are likewise non-droppable — same no-affordance treatment —
  **with one mandatory carve-out: the card's OWN current column is never disabled.** Dropping a
  card back on its home column is the pointer user's cancel path; it resolves as a no-op via
  `resolveBoardStage(item)` (D-05) — no mutation, no toast, no success signal. Without the
  carve-out, a home drop on a disabled column would retarget to the nearest enabled column — for an
  overdue card that can mean Done, a silent unintended write. The carve-out is a contract, not a
  suggestion.
- **Fallback (per the ruling's own hedge):** if the per-card predicate proves inexpressible in the
  installed dnd-kit, drop the affordance and keep the mutation-layer reject alone (candidate (a)),
  with the switch note in the plan. The oracle must PROVE expressibility, not assume it.
- Whether refusal remains the right interaction once `overdue` renders distinctly is Phase 96's to
  revisit (D-33 switch note) — carry the note, do not settle it here.

### 3. Degraded row state — `/after-actions` list entries whose join misses (D-13)

An after-action whose engagement/dossier lookup misses is **LISTED, never hidden** (the `!inner`
embed silently deleting rows is the confident-empty class Phase 93 closed). The row contract:

- The row renders in the table at normal `var(--row-h)` height, navigable to its detail page —
  identity first, from whatever the base record supplies.
- The ENGAGEMENT cell renders a named degraded label (key below) at Body size (13px/400) in
  `text-warn` — warn, not danger, because nothing failed; the record is incomplete (the P93 D-07
  discriminator). Any other cell whose value depends on the missed join renders an em dash `—`
  (the P93 count-placeholder vocabulary), never a fake value, never blank-that-looks-loaded.
- No `role="alert"` on a row — it is persistent informational state, not an interruption. No icon,
  no badge chrome, no new component: a translated string in an existing cell is the whole delta.
- The table keeps its existing chrome: `1px solid var(--line)` borders, no shadows, no gradients.

### 4. Translated error copy — the after-actions detail page (WRITE-02, D-08, D-10)

- `$afterActionId.tsx:65` currently renders the raw key `afterActions.loadError` (dot-form lookup
  into `common` where the key does not exist). The fix authors the key in `common.json` under the
  existing 228-key `afterActions` subtree — **in BOTH locales in the SAME commit** (key-set
  equality is the gate) — and converts the call to the COLON form
  `t('common:afterActions.loadError')`. Adding the key while keeping the dot form is the named trap
  (D-10); a fix that does that reproduces the bug class silently.
- The error surface itself reuses Phase 93's vocabulary: `QueryErrorState` page-level variant if
  the route's primary query failed (danger icon, `role="alert"`, one `.btn-primary` "Try again"),
  or the route's existing error region if one exists — never new markup.
- `$afterActionId.tsx:109` (`err.message ?? t('afterActions.publishFailed')`) — the raw message
  operand is removed; the EXISTING `publishFailed` key renders alone. Same repair class at the
  engagement route's save toast (`after-action.tsx:103`). Raw messages go to `console.error`.
- Sibling missing keys on the same page (`notFound`, `notFoundDescription`, the `conflict.*`
  group surviving on inline-English defaults) are repaired under the same key-set-equality rule if
  the plan touches those render paths; `loadError` is the criterion-bearing key.

### 5. Create-mode Save/Publish enablement — `AfterActionForm` (WRITE-01)

A disabled-button-state contract, not new chrome. Buttons keep their exact shipped recipes
(`AfterActionForm.tsx:480-510`: Save = outline variant, Publish = default accent-filled variant;
`Save`/`Send` icons with logical `me-2` spacing; `Loader2` spinner while pending).

| State                                                                             | Save draft                         | Publish                                           |
| --------------------------------------------------------------------------------- | ---------------------------------- | ------------------------------------------------- |
| Create mode, untouched empty form                                                 | disabled                           | disabled (visible when `canPublish && onPublish`) |
| Create mode, user has entered content                                             | **enabled** (the WRITE-01 fix)     | disabled until `isFormValid()`                    |
| `isFormValid()` true (≥1 attendee + ≥1 of decisions/commitments/risks/follow-ups) | enabled                            | **enabled**                                       |
| While saving or publishing                                                        | disabled, spinner + progress label | disabled, spinner + progress label                |

- The fix must NOT enable Save on an untouched empty form (deleting the `if (!initialData) return`
  guard naively does exactly that — the effect fires post-mount). Gate on content-derived dirtiness
  (the `hasContent` expression the file already computes at `:140-151`) or a skip-first-render
  pattern. Edit mode behaviour is unchanged.
- The engagement route passes `canPublish` + `onPublish`; `canPublish` mirrors **the SERVER's** role
  set — `['staff','supervisor','admin']`, `supabase/functions/after-actions-publish/index.ts:60-71`.
  A user without the role sees no Publish button at all — never a permanently disabled one.

  > **CORRECTED 2026-08-16 (`RULING-P94-07`).** This line previously read `['supervisor','admin']`
  > and cited "Assumption A2" — **the assumption `RULING-P94-04` overturned**, in favour of the
  > server set, on the grounds that the server is the enforcement boundary and a UI narrower than
  > the server is a hidden capability, not a policy. The spec was authored before that ruling and
  > was never re-synced, so this binding artifact contradicted both the ruling and `94-01`, which
  > implements the ruling correctly. Found by the round-2 plan-check.
  >
  > **The class, stated because it is not about this line:** C9 ("repoint every consumer in the same
  > edit") was applied to code artifacts and never to **rulings**. A ruling that overturns an
  > assumption must sweep the artifacts that encode it. **Full rulings-vs-spec sweep run in this
  > same edit** — population: every ruled decision in `RULING-P94-01..-06` checked against this
  > document. Result: **this was the only contradiction.** `A3` (tenant derivation),
  > `PARK-94-05` (edge-function query shape), `PARK-94-07` (probe identity) and `PARK-94-08` (audit
  > precondition subset) have **no rows here and correctly so** — they are not UI concerns, and this
  > spec's scope is the rendered surface. That absence is the population's boundary, not a gap.

- Publish from create mode is a two-step (create → publish) behind one button press; while it runs,
  BOTH buttons are disabled and the existing `publishing` label shows. On failure, the translated
  failure copy renders (contract 4) — never a raw message, never success-then-nothing.
