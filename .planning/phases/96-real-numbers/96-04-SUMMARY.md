## Decisions Made

- **Layout shape (a)**, as recorded above.
- **The wizard is gone, not re-gated.** UI-SPEC's contract is "grid, empty or not"; a wizard that only appears when a month is empty is the same defect with a narrower trigger.
- **`isRetrying` is real, not faked.** `useCalendarEvents` exposed no in-flight signal, so rather than pass a hardcoded `false` or reconstruct the query key with `useIsFetching`, the domain hook returns TanStack's `isRefetching` (additive; no consumer breaks). A retry button that never disables is a small lie in a phase about not telling small lies.
- **Fix the a11y defect, don't weaken the a11y spec.** `calendar-a11y` is red because it truthfully found violations in UI this change made reachable. Weakening it to green would be the forbidden shape.
- **`/events` cell-click behaviour preserved verbatim.** Clicking a day set the state that drove the month window (a no-op for an in-month day); after the rename it sets `currentMonth` to that day — identical semantics, zero new interaction invented.

## BLOCKED

**BLOCKED-1 — `.cal-cell.other` day numbers fail WCAG AA contrast (6 nodes, serious).**
Measured by axe on the now-reachable grid: `fgColor #686c73` on `bgColor #1b1d20`, **3.2:1** against a required **4.5:1**, at 14 px / normal weight. Cause is `frontend/src/components/calendar/calendar.css:39-41` — `.cal-cell.other { opacity: 0.4 }` dimming adjacent-month cells; `.cal-d` is already `var(--ink-mute)` before the dim.
Why not fixed here: this plan's Task 2 action (3) says **keep existing chrome as shipped**, and raising the dim is a visible design change to the shipped adjacent-month treatment. Changing it is a plan-semantics decision (rule 10), not an executor's.
What it needs: a ruling on the remedy — raise `opacity` to ≈0.6, or set an explicit accessible `.cal-cell.other .cal-d` colour and keep the dim on the pills only. Until then `calendar-a11y.spec.ts` (en + ar) stays red on this one violation class and no other.

**BLOCKED-2 — `calendar-rtl.spec.ts:75,77` assert Arabic-Indic digits against a ruled Latin-digits policy.**
`CalendarMonthGrid.tsx:98-100` renders `format(day, 'd')` (date-fns, no locale) inside `<LtrIsolate>` → Latin digits in both locales, which is the ruled policy (design review 260704; 96-UI-SPEC "Latin digits in both locales by policy"). The Phase-39 spec asserts the opposite and cannot pass against the shipped component under any data.
Why not fixed here: choosing which side is wrong — update the spec to the policy, or revert the policy for calendar day numbers — is a policy call, and this is neither a correct-change red from this task (the component's digit rendering is untouched by it) nor mine to rule.
What it needs: a ruling naming which of the two is authoritative for calendar day numbers; if the spec is stale, its `:75`/`:77` assertions invert in the same commit that records the ruling.

**BLOCKED-3 — `calendar-visual.spec.ts` (4 tests) has no committed baseline.**
`frontend/tests/e2e/calendar-visual.spec.ts-snapshots/` does not exist in HEAD, so every run fails with "A snapshot doesn't exist … writing actual" (VISUAL-DEBT-01 class). This change alters the `/calendar` pixels legitimately (grid instead of wizard), so a baseline captured now would bake in an unreviewed render.
Why not fixed here: committing a first baseline is a visual sign-off, and this plan carries no sign-off authority. The two accidental baseline sets Playwright wrote during triage were deleted, both times verified.
What it needs: a human render sign-off on `/calendar` at the four matrix points (ltr/rtl × 1280/768), after BLOCKED-1 is ruled — the contrast remedy will move those pixels again.
